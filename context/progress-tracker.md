## Architecture Decisions

- Prisma (05): Schema split into `prisma/schema.prisma` (generator + datasource) and `prisma/models/project.prisma` (models), picked up automatically by `prisma.config.ts` `schema: "prisma/"`. Generator uses `provider = "prisma-client"` (v7) with explicit `output = "../app/generated/prisma"`. `PrismaClient` requires an adapter in v7 — both the direct and Accelerate branches pass `new PrismaPg({ connectionString: url })`. The Accelerate branch additionally chains `.$extends(withAccelerate())`. `@prisma/extension-accelerate` is installed but the Accelerate branch is only active when `DATABASE_URL` starts with `prisma+postgres://`.
- Project APIs (06): Route handlers use Next.js 16 `params: Promise<{ projectId: string }>` (dynamic params are now Promises). Auth uses `const { userId } = await auth()` from `@clerk/nextjs/server` — not `auth.protect()` which returns 404 for unauthenticated API requests instead of 401. Owner enforcement is done by fetching only `{ id, ownerId }` before any mutation, comparing to `userId`, and returning 403 if they differ. DELETE returns `new Response(null, { status: 204 })` with no body.
- Wire editor home (07): `app/editor/page.tsx` is an async Server Component — no `"use client"`. Data is fetched with `getUserProjects()` from `lib/data/projects.ts` using Prisma + Clerk `auth()`. The Prisma return type is inferred with `Awaited<ReturnType<typeof prisma.project.findFirst>>` to avoid importing from generated client paths that differ from the barrel export. `useProjectActions` generates a unique room ID suffix with `Math.random().toString(36).slice(2,7)` concatenated after the slug. The sidebar now receives separate `ownedProjects` and `sharedProjects` arrays instead of a mixed `projects` array filtered internally.
- Liveblocks Setup (10): Declared typed interfaces for global `Liveblocks` state in `liveblocks.config.ts`. Cached the server-side `@liveblocks/node` client on `globalThis` during development to survive hot module reloads, similar to the Prisma client singleton pattern. Implemented deterministic hashing on user IDs in `getCursorColor` to consistently map collaborators to a specific color from our 9-color design palette. Secured the `/api/liveblocks-auth` route by requiring Clerk sessions and delegating authorization checks to the existing project-level `checkProjectAccess` helper before invoking `liveblocks.identifyUser`.
- Base Canvas (11): Spliced the client-side Liveblocks wrappers and the React Flow canvas to render collaboratively on `/editor/[roomId]` workspace pages. Structured types in `types/canvas.ts` mapping to `@xyflow/react` interfaces for custom node/edge contracts. Used global CSS imports for React Flow and Liveblocks component UI styles in the client canvas module to avoid polluting root layout scope.
- Design Agent API (22): `POST /api/ai/design` uses a type-only import (`import type { designAgent }`) + `tasks.trigger<typeof designAgent>("design-agent", payload)` — never imports the task instance into the Next.js bundle. `TaskRun` records are stored in PostgreSQL (not Blob) as first-class ownership metadata. `POST /api/ai/design/token` calls `auth.createPublicToken` from `@trigger.dev/sdk` (aliased as `triggerSdkAuth` to avoid collision with Clerk's `auth`) with `scopes.read.runs: [runId]` to issue the narrowest possible frontend token. Ownership is enforced by querying `TaskRun.userId` before any token issuance.
- Design Agent Logic (23): Canvas mutations from the Trigger.dev background task use `mutateFlow` from `@liveblocks/react-flow/node` (not the JSON Patch REST API), which accepts the same `Liveblocks` node client used in `lib/liveblocks.ts` and handles LiveMap/LiveObject internals correctly. AI presence is published via the Liveblocks REST ephemeral presence endpoint (`POST /v2/rooms/{roomId}/presence`) — the agent appears in `useOthers` alongside human collaborators with a 120s TTL. Status progress is broadcast via `POST /v2/rooms/{roomId}/broadcast`; clients subscribe with `useEventListener` typed against the updated `RoomEvent` union in `liveblocks.config.ts`. The LLM is constrained to a Zod discriminated-union schema (`CanvasActionSchema`) so output is always structured and type-safe before any canvas mutation occurs.
- AI Provider Migration (23-followup): Replaced `@ai-sdk/google` with `@openrouter/ai-sdk-provider` to utilize OpenRouter's free model pool (`"nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free"`). Configured OpenRouter-specific reasoning options via `providerOptions.openrouter` in `generateObject` for standard Vercel AI SDK provider parameter passing. Used `OPENROUTER_API_KEY` for API key authentication.
- Feed Reliability (E2E connection): Liveblocks feeds must be explicitly created via `createFeed` before any `createFeedMessage` call — otherwise the server returns a 500. Two initialization paths exist: (1) The `/api/liveblocks-auth` route pre-creates feeds during room authentication, covering the case where a user joins before any agent runs. (2) The `design-agent` Trigger.dev task pre-creates all three feeds (`ai-status-feed`, `ai-chat`, `room-chat`) at the start of each run, covering the case where the agent worker executes before any user has authenticated to the room. The `safeFeedMessage()` helper provides a third layer of defense by calling `createFeed` (idempotent) before every write. This belt-and-suspenders approach ensures feeds always exist regardless of initialization ordering.
